OTP: ผู้ใช้กรอกเองในแอป ชุดทดสอบไม่ต้องได้รับ OTP ผ่านแชตหรือไฟล์ ไม่อ่านช่อง OTP และไม่จับภาพหน้ากรอก OTP หลังผู้ใช้เริ่มกรอก

ก่อนขั้นสมัครหลักให้ออกจากบัญชีที่ค้างอยู่ผ่านเมนูแอป ไม่ถอนติดตั้ง ไม่ลบข้อมูลแอป และไม่ลบบัญชีอัตโนมัติ หากอีเมลที่เพิ่งลบบัญชียังสมัครไม่ได้ ให้บันทึกผลผิดพลาดของระบบจริง ห้ามเปลี่ยนเป็นทดสอบ login แล้วนับว่าผ่านการสมัครใหม่

## รูปแบบการทำงาน

- ตัวรันใช้ `--no-uninstall` เพื่อคงแอปและ secure storage หลังจบการทดสอบ ใช้ session บัญชีหลักเดิมต่อเมื่อยังใช้งานได้ ไม่ logout หรือเปลี่ยนบัญชีเว้นแต่กรณีทดสอบจำเป็นต้องใช้บัญชีรองหรือยืนยันตัวตนใหม่
- ตาราง Beginner ที่ทดสอบ: Easy Run 3 วัน และ Long Run 1 วัน ตรวจครบทั้งสี่รายการก่อนกดบันทึก

- `register-primary`: ชุดเดิมกดสมัคร ยอมรับนโยบาย กรอก Onboarding และ Wellness ให้โดยอัตโนมัติ รอผู้ใช้กรอก OTP เอง ตรวจชื่อและ UID ที่โปรไฟล์ด้วย
- รอบอื่นเป็น **guided integration test**: ผู้ทดสอบหรือผู้ควบคุมแอปทำรายการผ่านหน้าจอจริงตามข้อความใน `.uat-runtime/bridge.log`; สคริปต์ตรวจบัญชี สถานะจริงจาก API และเงื่อนไขที่ระบุ พร้อมเก็บภาพเมื่อ assertion ผ่าน ไม่ใช้ API เขียนข้อมูลแทนการกดหน้าจอ
- ไม่ใช้ mock ไม่ข้ามยืนยันตัวตน ไม่เพิ่มเหรียญให้ตัวเอง ไม่สร้างเส้นทาง GPS จำลอง และไม่มีคำสั่งลบบัญชี
- ขั้น `setup-secondary` รอให้ผู้ใช้เข้า/สมัครและทำ Onboarding ให้ครบ ถ้ามีข้อมูลเดิมใช้ข้อมูลเดิมโดยไม่เขียนทับอัตโนมัติ
- แต่ละรอบต้องใช้บัญชีตามตาราง ถ้าค้างอยู่บัญชีอื่นให้ผู้ควบคุมออกแล้วเข้าใหม่ในแอป สคริปต์จะรอจน email ตรงก่อนตรวจข้อมูล
- รหัส UID/คลับ/คำขอเพื่อนเก็บเฉพาะตัวระบุที่ไม่ใช่ความลับใน `frontend/.uat-runtime/live-context.json` แยกตาม API environment; เริ่มแผนใหม่ต้องตรวจว่าเป็น UID ของบัญชีปัจจุบัน
- ผู้ดูแลต้องอ่านคำแนะนำจาก log และทำรายการเป็นลำดับจนมี checkpoint ก่อนเริ่มขั้นถัดไป โดยเฉพาะ `verify-secondary` ต้องเปิดคลับแล้วรอให้เครื่องมือเห็นหน้าที่ออกจาก Home ก่อนกลับ Home

## เตรียมอย่างเดียว — ทำได้ทันทีโดยไม่ติดต่อระบบ

จากโฟลเดอร์ `frontend`:

```powershell
.\tool\prepare-live-uat.ps1
```

สร้าง `.uat-runtime/prepared-plan.json` ซึ่งมี 88 Case ID เริ่มเป็น Not Run ไม่เปิดแอป ไม่เรียก adb ไม่ส่งอีเมล และไม่ติดต่อ API

## คำสั่งใช้ภายหลังเมื่อผู้ใช้บอกให้รันจริง

รองรับ Android ที่เชื่อมต่อ adb ในชุดนี้; iOS ยังไม่มี runner ที่เตรียมไว้

กรอก Device ID และ URL ที่จะใช้จริงก่อนเริ่ม ไม่เดาค่าให้และไม่เรียก API เพื่อค้นหาอัตโนมัติ จากนั้นเรียกทีละ phase ไม่วนรันซ้ำโดยไม่ตรวจสถานะก่อน เพราะบัญชีและข้อมูลจะเปลี่ยนจริง

```powershell
$uatDeviceId = '<DEVICE_ID>'
$uatApiUrl = '<API_BASE_URL>'
.\tool\prepare-live-uat.ps1 -Phase register-primary -DeviceId $uatDeviceId -ApiBaseUrl $uatApiUrl -Execute
```

เปลี่ยน `-Phase` ตามลำดับในตารางด้านล่าง ใช้ API เดิมและข้อมูลชุดเดียวกันตลอดแผน:

| ลำดับ | Phase | บัญชี | สิ่งที่ทำและตรวจจริง |
|---|---|---|---|
| 1 | register-primary | หลัก | สมัครใหม่ → กรอก OTP เอง → Onboarding เพิ่มความอึด ไม่มีเป้าระยะ → Wellness → โปรไฟล์ |
| 2 | setup-secondary | รอง | เข้า/สมัครตามสถานะจริงและกรอก OTP เอง → จบ Onboarding → บันทึก UID รอง |
| 3 | program | หลัก | ต้องเช็กอินวันนี้แล้วและไม่มีโปรแกรม active → สมัคร/จัด/บันทึกตาราง → ตรวจข้อมูลสัปดาห์จากระบบจริง |
| 4 | run | หลัก | ต้องมีแผนวันนี้ที่เริ่มวิ่งได้ → ผู้ทดสอบวิ่ง GPS จริงหรือลู่วิ่ง → จบและ RPE → ตรวจมี session ใหม่เพียงรายการเดียว → เปิดสถิติ/อันดับและตรวจ API |
| 4a | run-park | หลัก | เลือก Park → รออย่างน้อย 5 วินาทีและให้แอปได้รับ GPS จริงผ่าน countdown → รอเวลาเดินอย่างน้อย 5 วินาที → จบโดยไม่กรอกระยะ → RPE → ตรวจสรุป/รางวัล/ประวัติ/สถิติ/อันดับ; อยู่กับที่ระยะเป็นศูนย์ได้ |
| 5 | profile | หลัก | เปิดโปรไฟล์ → แก้ชื่อให้ต่างจากเดิม → ตรวจชื่อบนหน้าจอและ API โดย UID ไม่เปลี่ยน |
| 6 | primary-social | หลัก | ต้องยังไม่เป็นเพื่อน/ไม่มีคำขอค้างกับรองและยังไม่มีคลับ → ส่งคำขอหา UID รอง → รอ checkpoint → สร้างคลับตามชื่อที่กำหนด |
| 7 | secondary-social | รอง | ต้องมีคำขอจากหลักและรองยังไม่มีคลับ → รับเพื่อน → รอ checkpoint → ค้นคลับหลักแล้วกดขอเข้า |
| 8 | approve-club | หลัก | ตรวจหลักเห็นเพื่อนที่ตอบรับ → อนุมัติคำขอรอง → ตรวจจำนวนสมาชิกเพิ่มหนึ่งและรองมีบทบาท member |
| 9 | verify-secondary | รอง | อ่านสมาชิกจาก API → เปิดคลับของฉัน → รอเครื่องมือเห็นหน้า → กลับ Home ตรวจผลจากฝั่งรอง |
| 10 | shop | หลัก | ระบุสินค้าและเตรียมเหรียญพอก่อน → ซื้อของที่ยังไม่มี → ตรวจหักราคาจริง → สวมแล้วบันทึกและตรวจ item/slot |

กรณีคลับ ชื่อเริ่มต้นคือ `Pacegasus UAT` หากชื่อนี้มีผู้ใช้แล้วให้เลือกชื่อทดสอบใหม่ด้วย `-ClubName 'ชื่อที่กำหนด'` ใน phase `primary-social` ชื่อจริงจะถูกเก็บไปให้ phase รองค้นต่อ ไม่ยุบคลับใครเพื่อเคลียร์ชื่อ

กรณีร้านค้าต้องเลือก `listingId` ของสินค้าจริงก่อน เครื่องมือไม่เลือกของราคาแพง/ใช้เหรียญเอง และหยุดหากเหรียญไม่พอหรือเป็นเจ้าของแล้ว:

```powershell
.\tool\prepare-live-uat.ps1 -Phase shop -DeviceId $uatDeviceId -ApiBaseUrl $uatApiUrl -ShopListingId '<LISTING_ID>' -Execute
```

ระหว่างตรวจเหรียญอย่าทำกิจกรรมรับรางวัลหรือซื้อสินค้าอื่น เพื่อให้เปรียบเทียบยอดก่อน−ราคาสินค้าได้ตรง

## หลักฐานและข้อจำกัดของผล

- เก็บแต่ละรอบที่ `output/uat/automated/<เวลาไทย>/` มี `results.json`, `UAT-REPORT.md` และภาพ checkpoint
- `passed` ในรายงานหมายถึง assertions ที่ระบุใน phase นั้นเท่านั้น คำว่า partial ระบุว่าเป็นเพียงบางเงื่อนไขของ Case ID ที่อ้างอิง
- แผน 88 กรณีใน `prepared-plan.json` เป็นทะเบียนแยก ไม่ถูกเปลี่ยนเป็น Pass ทั้งหมดอัตโนมัติ การตรวจ flow หลักไม่แทนการตรวจ OTP ผิด/หมดอายุ ขอบเขตค่า เน็ตหลุด สิทธิ์ทุกบทบาท หรือคำนวณสถิติทุกชุดข้อมูล
- การเปิดหน้าสถิติ/อันดับร่วมกับ API assertions ยังไม่ใช่การตรวจว่าตัวเลขทุกตำแหน่งบนหน้าจอถูกต้อง ผู้ทดสอบต้องบันทึกผลการเทียบภาพและตัวเลขตามเอกสาร 88 กรณีเพิ่มเติม
- ไม่ทำ reset/cleanup ที่ลบความสัมพันธ์ โปรแกรม หรือคลับอัตโนมัติ ถ้าข้อมูลเคยผ่านแล้วจะให้ตรวจเงื่อนไขก่อนรันใหม่ แทนการรับรองว่าสร้างใหม่สำเร็จจากข้อมูลเก่า
- กรณีคนนอกบัญชีที่สาม คลับเต็ม 20 คน อันดับเกิน 50 คน เปลี่ยนสัปดาห์ และจำลองความผิดพลาด ต้องเตรียมข้อมูล/ทำตาม manual cases ภายหลัง ยังเป็น Not Run
- ถ้าวิ่งข้ามสัปดาห์ระหว่าง phase ให้แยกการตรวจอันดับเป็นรอบใหม่ตามช่วงเวลาไทย เพราะ session ใหม่อาจไม่อยู่ในสัปดาห์ที่กำลังแสดง
- ปัญหาหรือ timeout ทำให้ phase ล้มเหลว ขั้นที่เหลือไม่ถือว่าผ่าน หลักฐานเป็นข้อมูลบัญชีทดสอบจริง ควรตรวจภาพก่อนส่งต่อ
